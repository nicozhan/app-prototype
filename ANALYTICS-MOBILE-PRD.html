01

结论与范围

先看这一页

Web 端的「报表与分析」共 7 个模块 20 个 Tab，但真正被后端接口支撑的只有销售金额、订单数、排行、设备资产四类。手机的定位不是把 Web 报表缩小，而是只做接口已经能给的、店员在店里会看的那部分。

可复用

5 个接口撑起 4 个页面

/api/v1/dashboard/* 的 summary、sales-trend、rankings、device-fleet-insights、device-activation-trend 全部现成；再加平台侧 usage-analysis 做 P1 漏斗。

可覆盖

Web P0 的 1 完整 + 5 部分

12 个 P0 Tab 里，1 个能完整还原、5 个能还原主要结论（口径降级为“金额/资产”）、5 个现有接口做不了、1 个属咖啡本期排除。

不做

渠道、退款、SKU 明细

这三类在 Web Demo 里有设计，但后端没有对应聚合接口。手机端不硬凑，明确留到二期，避免出现“有图无数据”。

1.1 本期要解决的三个问题

  1. 今天卖得怎么样？——补货前 / 巡店时看销售额、订单、客单价与环比，30 秒内判断“要不要多补”。
  2. 什么卖得好？哪个点位强？——商品、点位、设备三个金额排行，决定主推与补货优先级。
  3. 设备资产健康吗？——设备/点位总量、活跃数、低库存、机型与固件分布、可升级台数。

2.2 一句话总结 Web 的分析结构

  • 四个视角：时间（趋势）、对象（商品 / 点位 / 设备）、渠道（支付）、资产（设备与机队）。
  • Web 的强项在“拆”：拆渠道、拆退款、拆识别状态、拆货道；这些都需要专门的聚合表，手机端短期拿不到。
  • Web 的弱项在“现场”：信息密度高、需要横向表格、必须桌面看。手机要的是结论 + 一眼对比，所以只保留金额/订单/排行/资产四条主线。

4.1 导航规则

  • 一级：A1 是唯一入口；A2/A3/A4 由 A1 的卡片标题右侧「详情 ›」进入，返回回 A1，并保留时间筛选。
  • 筛选继承：A1 选“近 30 天”后进 A2，A2 初始也是“近 30 天”；在 A2 改筛选，返回 A1 时同步（同一份 range 状态）。
  • 深链：analytics?range=month&tab=rank 可直接打开对应状态，供首页汇总卡跳转使用。
  • 角色：租户角色只看本租户；平台角色可切租户（沿用 App 现有租户切换器），A5 仅平台角色可见。

转化漏斗（P1 试点，仅平台角色）

P1 · 2 天
为什么放 P1
这是现有数据里最“值钱”的一块（货架浏览 → 支付成功 → 取货），但 usage-analysis 只对平台角色开放，且必须指定租户。租户运营账号看不到。
口径
五个数的关系是逐级包含，不是独立指标；比值只在同一设备同一区间内成立。人流三项为 null 时显示「—」。
限制
单次最多 30 天；按设备逐日返回，客户端按区间求和（注意不要按天平均）。
不做
不做“转化率诊断建议”、不做同比；本期只做“看得见”。
数据源
GET /api/v1/operations/usage-analysis

自定义from/to 用户选择range=custom&from&to等长前移（天数）

日期一律用设备本地日期（YYYY-MM-DD），不加时区后缀；服务端按租户时区归日。自定义区间上限 90 天，超出提示“最多查看 90 天”。

6.2 派生指标公式

指标公式边界
客单价totalSalesAmount ÷ totalOrderCount订单为 0 时显示「—」，不显示 ¥0.0
环比(本期 − 上期) ÷ 上期 × 100%上期为 0 或缺失 → 显示「—」，不显示 +∞ / +100%
排行占比该行 salesAmount ÷ 本期 totalSalesAmount总额为 0 → 不显示占比条
日均区间合计 ÷ 区间天数（含今天）points 少于天数时按实际点数算，并标注
峰值points 中 salesAmount 最大的一条并列取最近一天

6.3 数字与文案规范

  • 金额：¥ + 千分位，一律不缩写（¥1,284,000），避免运营对不上后台；只有图表纵轴例外，用 12.8k。
  • 订单/设备数：千分位；小数不出现。
  • 币种：接口只返回一个 currency，页面在 KPI 标题后标一次（如“CNY”），不做多币种分组——与 Web 的多币种分组是不同层级，不要混。
  • 涨跌色：上升绿 #008f63、下降红 #d92d20，与 Web 报表一致。注意：这与库存盘盈亏的红绿语义相反，不要跨模块复用同一个组件属性。
  • 空值：一律「—」；只有真实为 0 才显示 0。
  • 禁用词：不出现“销量”“件数”“退款率”“转化率”“动销”，除非对应接口已上线。

6.4 缓存与刷新

  • 同一 (tenantId, from, to) 的 summary / rankings / trend 结果缓存 60 秒；切 Tab 不重复请求。
  • 下拉刷新清空缓存并重发；A2 返回 A1 时若 range 未变，直接用缓存。
  • 首屏并行 4 个请求，任一失败只降级对应卡片，不整页报错。

场景处理

date_range_required属于客户端 bug（from/to 未成对），开发期断言拦截；线上回退到“近 7 天”并上报。
custom_range_required自定义必须同时带 from 与 to；日期选择器未选完整时禁用“确定”。

金额币种与租户不符以接口 currency 为准展示，不做前端换算。

9.2 风险与依赖

风险 / 依赖影响应对
运营角色默认没有 dashboard:read高上线前在后台角色里补权限；这是配置项，不算新接口。上线前用真实运营账号回归一次。
“今日”按服务端日期切分中现接口 todaySalesAmount 用服务端 LocalDate.now()，与租户时区可能差几小时。手机端沿用同口径并在页脚说明，不在前端重算。
排行只有金额，没有销量中统一叫“销售额排行”，文案与图例都不提销量；二期再加 quantity 字段。
单币种返回中接口只回一个 currency；跨境租户在手机上看到的是“最近一个币种”，与 Web 的多币种分组不一致，需在页脚注明。
数据新鲜度低销售日报在订单完成时滚动汇总，通常分钟级；今日数字可能滞后，页脚注明“数据实时汇总，可能有数分钟延迟”。
设备/点位/商品数量含咖啡机中summary.operational 没有设备类型参数，计数为租户全量。页面文案写“租户全部设备”，不写“仅预包装”；分机型交易本期本就不做。
usage-analysis 仅平台角色中A5 只对平台账号开放；租户账号不展示入口，避免“点进去是 403”。
